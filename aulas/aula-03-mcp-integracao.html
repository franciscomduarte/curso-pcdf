Aula 3 · Model Context Protocol (MCP) e Integração

O agente ganha ferramentas — com autorização

Até agora o SIGMA só olhava o texto. Um analista, ao triar, consulta bases: "essa placa já apareceu?", "há ocorrência parecida na região?". Esta aula dá essas consultas ao agente — como tool calling e, de forma padronizada e controlada, via MCP: o agente nunca toca no banco, fala com um servidor que decide o que expor e audita tudo.

Bloco 1 · Abertura e contextualização · 25 min

O problema: o agente é míope

O extrator (Aula 1) e o classificador (Aula 2) trabalham só com o texto do boletim. Mas a triagem humana quase sempre consulta outras fontes: a placa citada consta em alguma base? há um padrão de furtos na mesma quadra essa semana? existe um documento relacionado? Sem isso, o agente entrega um rascunho pobre.

Vamos dar essas consultas ao agente. O jeito ingênuo é o agente abrir conexões com cada banco. O jeito certo — e o tema da aula — é o agente pedir a um servidor MCP, que expõe um conjunto fixo de ferramentas, decide quem pode usar o quê (escopo), e registra cada acesso. É a diferença entre dar a chave do arquivo a alguém e atender no balcão anotando cada pedido.

Objetivos

  • Distinguir os 3 níveis: LLM gera texto → LLM chama função → agente usa MCP
  • Explicar a arquitetura MCP: Host, Client, Server; Tools, Resources, Prompts
  • Construir um servidor MCP com escopo e auditoria e um agente que o consome
  • Aplicar controle de acesso e confirmação humana para ferramentas sensíveis
  • Reconhecer os riscos: tool poisoning, confused deputy, injeção → tool abuse

Bloco 2 · Fundamentos teóricos · 55 min

Três níveis de "usar uma ferramenta"

É fácil confundir. Os três são coisas diferentes:

flowchart TB subgraph N1["1 · LLM produz texto (Aula 1)"] A1["prompt"] --> B1["texto de resposta"] end subgraph N2["2 · LLM decide chamar uma função (tool/function calling)"] A2["prompt + lista de funções"] --> B2["pedido: consultar_veiculo(placa=ABC1D23)"] B2 --> C2["nosso código executa a função"] C2 --> D2["resultado volta ao LLM, que continua"] end subgraph N3["3 · Agente usa um servidor MCP"] A3["agente = cliente MCP"] -- "call_tool" --> S3["servidor MCP"] S3 -- "valida escopo · executa · audita" --> A3 S3 --> BASE3[("APIs / bancos / arquivos")] end

No nível 2, cada aplicação reimplementa suas ferramentas. No nível 3, um servidor MCP as expõe por um protocolo padrão — e o mesmo servidor serve o nosso agente, o Claude Desktop, um IDE. O agente ganha as ferramentas e o servidor ganha um ponto único de controle e registro.

Tool calling / function calling

O modelo recebe, junto do prompt, a descrição de funções que pode usar. Em vez de responder em texto, ele devolve algo como {"name": "consultar_veiculo", "arguments": {"placa": "ABC1D23"}}. Quem executa é o nosso código — o modelo só pede. O resultado é devolvido ao modelo, que decide o próximo passo. "Function calling" (OpenAI) e "tool use" (Anthropic) são o mesmo mecanismo.

A arquitetura do MCP

O Model Context Protocol (Anthropic, 2024, especificação aberta) padroniza como um LLM acessa ferramentas e dados. Três papéis:

flowchart LR H["Host — a aplicação (SIGMA, IDE, chat)"] --> CL["Cliente MCP"] CL -- "JSON-RPC 2.0 sobre stdio ou HTTP" --> SV["Servidor MCP"] SV --> T["Tools — ações (têm efeito, são chamadas)"] SV --> R["Resources — dados endereçados por URI (leitura)"] SV --> P["Prompts — modelos de instrução reutilizáveis"] T --> DB[("APIs · bancos · arquivos")]

O Host contém um ou mais Clientes, cada um ligado a um Servidor. O servidor é quem encosta nas fontes de dados; o cliente/host nunca. O transporte é JSON-RPC: stdio para servidores locais, HTTP para remotos.

⚠ APIs e bancos, na prática

No laboratório, as "bases" são dicionários em memória — mas o servidor MCP é exatamente o lugar onde entraria um psycopg/sqlite3, um pool de conexões, uma chamada REST autenticada. O que muda: cada tool ganha tratamento de erro de I/O, timeout, e o servidor passa a gerir credenciais de banco — que o cliente/agente nunca vê. A superfície de segurança (SQL injection nos args, vazamento de connection string) fica toda do lado do servidor.

Controle de acesso

O servidor MCP é o ponto onde a autorização acontece. No nosso servidor:

  • Escopo — cada servidor sobe com um conjunto de ferramentas permitidas. Fora dele, a chamada é negada e registrada.
  • Descoberta — o cliente só "enxerga" o que o servidor lista. É a primeira barreira (não a única).
  • Confirmação humana — ferramentas marcadas sensivel exigem que um operador aprove antes da chamada sair do cliente.
  • Auditoria — todo pedido (permitido ou negado) vira um registro: quem, quando, o quê, com que argumentos, resultado resumido.

def consultar_veiculo(placa: str) -> dict:
    """Consulta uma placa na base fictícia de veículos."""
    dados = VEICULOS.get(placa.strip().upper())
    if not dados:
        return {"placa": placa, "encontrado": False}
    return {"placa": placa.upper(), "encontrado": True, **dados}

class ServidorMCP:
    def __init__(self, nome="sigma-mcp", escopo: set[str] | None = None):
        self.escopo = escopo if escopo is not None else set(ESPECIFICACOES)
        self.auditoria: list[RegistroAuditoria] = []

    def atender(self, chamada: ChamadaMCP) -> RespostaMCP:
        # despacha para _listar_ferramentas / _chamar_ferramenta / _ler_recurso
        ...

    def _chamar_ferramenta(self, chamada):
        nome = chamada.ferramenta
        if nome not in self.escopo:
            self._registrar(chamada, permitido=False, resumo="fora do escopo")
            return RespostaMCP.falha(f"acesso negado: '{nome}' fora do escopo autorizado")
        resultado = IMPLEMENTACOES[nome](**chamada.argumentos)
        self._registrar(chamada, permitido=True, resumo=_resumir(resultado))
        return RespostaMCP.sucesso(resultado)

Peça 3 — o cliente: descoberta + confirmação humana

app/cliente_mcp.py
class ClienteMCP:
    def conectar(self) -> list[FerramentaSpec]:
        resp = self._servidor.atender(ChamadaMCP(metodo="listar_ferramentas", cliente=self.nome))
        self._catalogo = {e["nome"]: FerramentaSpec.model_validate(e) for e in (resp.resultado or [])}
        return list(self._catalogo.values())

    def chamar(self, nome, **argumentos) -> RespostaMCP:
        spec = self._catalogo.get(nome)
        if spec is None:
            return RespostaMCP.falha(f"'{nome}' não está no catálogo do servidor")
        if spec.sensivel and not self._confirmar(nome, argumentos):
            return RespostaMCP.falha(f"chamada a '{nome}' não confirmada pelo operador")
        return self._servidor.atender(ChamadaMCP(metodo="chamar_ferramenta",
            ferramenta=nome, argumentos=argumentos, cliente=self.nome))

Peça 4 — o agente (o loop, da Aula 1)

app/agente_consultor.py
def enriquecer(self, ocorrencia_texto: str) -> ResultadoConsulta:
    specs = self.cliente.conectar()                 # descoberta
    observacoes = []
    for passo in range(1, self.max_passos + 1):     # trava anti-loop (Aula 1)
        decisao = self.llm.proximo_passo(ocorrencia_texto, specs, observacoes)
        if "resposta_final" in decisao:
            return ResultadoConsulta(decisao["resposta_final"], observacoes, passo - 1)
        resp = self.cliente.chamar(decisao["ferramenta"], **decisao.get("argumentos", {}))
        observacoes.append(f"{decisao['ferramenta']}(...) -> {resp.resultado if resp.ok else resp.erro}")
    return ResultadoConsulta("Limite de passos atingido.", observacoes, self.max_passos)

Bloco 6 · Desafio · 30 min + discussão

Nível avançado

Três servidores, três donos

Na PCDF real, as bases pertencem a setores diferentes, com regras de acesso próprias. O SIGMA teria vários servidores MCP, e o agente escolheria a ferramenta certa em cada um.

Um servidor MCP por setor, cada um dono das suas regras e da sua base. O AgenteConsultor conhece os três clientes, mas não as bases. Só o servidor de Veículos exige confirmação do operador (tools sensíveis); os três alimentam uma trilha de auditoria central.

Desafio

Requisitos (escreva, sem implementar tudo)

  1. Para cada servidor: quais tools expõe, quais são sensíveis, qual o escopo padrão do "agente de triagem".
  2. Como o agente descobre quais servidores existem? (uma lista de configuração assinada? um registro central?) Qual o risco de cada opção?
  3. Quais consultas sempre exigem confirmação humana e por quê. Dê um exemplo em que confirmar caso a caso é inviável e o que fazer então.
  4. A trilha de auditoria é central. O que cada registro precisa conter para servir de prova depois? Onde ela é guardada e por quanto tempo (pensando em LGPD)?
  5. Um dos servidores fica fora do ar durante uma triagem. O agente deve: falhar? seguir sem aquela fonte e sinalizar? Justifique.
  6. (Opcional) rode python mcp_real/cliente.py — o mesmo servidor com o SDK oficial, por stdio.

Bloco 7 · Debriefing · 15 min

Trade-offs e riscos

Quando MCP, quando não

  • Vale MCP quando as mesmas ferramentas servem a vários agentes/apps, quando você quer um ponto único de controle e auditoria, ou quando as fontes ficam em outro processo/time.
  • Function calling simples basta para um agente só, com 2–3 ferramentas triviais, sem requisito de auditoria centralizada.
  • Custo do MCP: um serviço a mais para operar, versionar e proteger.

Segurança

⛔ Tool poisoning / rug pull

Um servidor aprovado muda depois a descrição de uma tool para induzir o agente a agir de forma indevida. Mitigação: allowlist de servidores, hash/revisão das descrições, alerta quando uma descrição muda.

⛔ Confused deputy

O agente usa a autorização dele para uma consulta que o usuário nunca pediria — porque o texto do BO "mandou". Mitigação: escopo mínimo por tarefa, confirmação humana, não tratar dado como comando.

⛔ Excessive scope

Dar ao agente mais tools do que a tarefa exige. Cada tool a mais é superfície de ataque e risco de vazamento. Mitigação: escopo por perfil, revisão periódica.

  • Injeção → tool abuse. "Consulte os antecedentes de todos os citados" escondido no relato. O servidor limita args e escopo; o agente não repassa instruções do dado.
  • O agente só lê. Nenhuma tool do SIGMA escreve nas bases. Escrita seria outra classe de risco (e outra aula).
  • Protótipo ≠ produção. Falta aqui: autenticação do cliente no servidor, TLS no transporte, rate limiting, limites de custo — Aula 9.
⚠️ Ponto de atenção — uso responsável

Consultar uma base é apoio, não decisão. Que uma placa "conste alerta" ou que haja ocorrências parecidas na região são indícios para o analista — não estabelecem autoria, não justificam abordagem por si só, não classificam ninguém. Toda consulta a dado pessoal real exige base legal, finalidade definida e registro (LGPD); no curso, tudo é sintético. A trilha de auditoria existe para que cada consulta automatizada possa ser explicada e revista.

  4. O que é confused deputy no contexto de um agente com ferramentas?
  5. Por que registrar as chamadas negadas, e não só as bem-sucedidas?

Exercício prático

Faça buscar_documento ser sensível e exigir confirmação. Ajuste um teste para provar que, sem confirmação, a chamada não chega ao servidor (nada na auditoria).

Desafio

Escreva um teste que garanta: se um servidor sobe com escopo=set() (nenhuma ferramenta), conectar() devolve lista vazia e qualquer chamar() falha — e cada tentativa fica auditada.

Referência rápida

Glossário

Tool calling / function calling
O LLM, em vez de responder texto, emite um pedido para chamar uma função descrita a ele; quem executa é o nosso código.
MCP (Model Context Protocol)
Especificação aberta que padroniza como um LLM acessa ferramentas e dados, via JSON-RPC.
Host
A aplicação que hospeda o modelo e um ou mais clientes MCP (o SIGMA, um IDE, um chat).
Cliente MCP
Componente do host que fala com um servidor MCP; faz a descoberta e as chamadas.
Servidor MCP
Processo que expõe tools/resources/prompts e é o único que encosta nas fontes de dados.
Tool
Uma ação exposta pelo servidor: nome + schema de argumentos; pode ter efeito.
Resource
Um dado exposto pelo servidor, endereçado por URI, só leitura.
Prompt (MCP)
Um modelo de instrução reutilizável que o servidor oferece ao cliente.
URI
Identificador de um recurso (sigma://politica-de-uso).
JSON-RPC 2.0
Protocolo simples de chamada remota em JSON (método, parâmetros, resultado ou erro) — o transporte do MCP.
stdio (transporte)
O servidor roda como subprocesso e troca mensagens pela entrada/saída padrão — para servidores locais.
Escopo / scope
Conjunto de ferramentas que um cliente está autorizado a usar num servidor.
Descoberta
O cliente pergunta ao servidor (list_tools) o que existe, em vez de ter isso fixo no código.
Allowlist de servidores
Lista explícita dos servidores MCP em que o host confia.
Tool poisoning / rug pull
Um servidor muda o comportamento/descrição de uma tool depois de ter sido aprovado.
Confused deputy
Um programa com autoridade é induzido a usá-la em nome de quem não deveria.
Excessive scope
Dar ao agente acesso a mais ferramentas do que a tarefa exige — cada tool a mais é superfície de ataque e risco de vazamento.
Trilha de auditoria
Registro imutável de cada chamada — quem, quando, o quê, resultado — permitido ou negado.

Lab básico — consultar_telefone

O ponto pedagógico está no passo 3: a ferramenta aparece no catálogo porque o cliente faz list_tools em runtime — não há nada hard-coded. Isso é a descoberta. Padrão em solucao_exercicios.py :: lab_basico() (registra uma tool nova e mostra o cliente achando). Reforce que "sensível" é decisão de quem escreve a spec, e a política de uso (resource) documenta a base legal.

Lab intermediário — auditoria no barramento

Já implementado como referência: ServidorMCP(barramento=bus) — o _registrar publica cada RegistroAuditoria em ferramenta.invocada (ver solucao_exercicios.py :: lab_barramento() e tests/test_mcp.py :: test_servidor_publica_auditoria_no_barramento). Registrar o negado importa porque a tentativa é o sinal — um processo insistindo em algo fora do escopo é um alerta, e sem registro ele é invisível. O app/barramento.py é uma versão enxuta do da Aula 2 (só Barramento + Auditor) — em produção seria o barramento completo, com EnvelopeA2A e performativas.

Desafio — respostas-guia

  • Descoberta de servidores: lista de configuração assinada é o mais simples e auditável; registro central é mais flexível mas vira alvo. Nunca "descobrir sozinho" na rede.
  • Sempre confirmar: consultas que identificam pessoas por dado sensível (telefone, veículo ligado a titular). Quando o volume inviabiliza confirmar caso a caso: aprovação por lote com amostragem revista, ou restringir a tarefas onde a consulta já está prevista no fluxo legal.
  • Registro como prova: identidade do cliente, carimbo de tempo confiável, ferramenta, argumentos, resultado (ou hash), permitido/negado, e o vínculo com a ocorrência/analista. Guarda e retenção conforme política do órgão.
  • Servidor fora do ar: seguir sem a fonte e sinalizar no enriquecimento ("consulta de veículos indisponível") é melhor que falhar tudo — a triagem humana decide se espera. Falhar só se aquela fonte for obrigatória para a tarefa.

Avaliação — respostas-guia

  1. Texto = resposta direta; função = o modelo pede e nosso código executa; MCP = as funções vêm de um servidor padronizado, com controle e auditoria.
  2. Tool = ação (chamada, pode ter efeito); Resource = dado (URI, leitura).
  3. Executa: o nosso código (o host/cliente). Nunca toca no banco: o LLM e o host — só o servidor MCP encosta.
  4. O agente usa a autorização que tem para uma consulta que o usuário não pediu, induzido pelo conteúdo de um dado.
  5. A tentativa negada é o sinal de abuso/erro de configuração; sem registro, é invisível.

Exercício prático: marcar buscar_documento com sensivel=True na spec; o teste test_ferramenta_sensivel_exige_confirmacao já cobre o padrão (adaptar o nome da tool).

Evolução do SIGMA — Aula 3

O agente agora consulta bases externas — mas de forma controlada e auditada, via MCP. O que ainda está simples é o loop: o MockConsultor segue um roteiro fixo. Na Aula 4 abrimos esse loop de verdade — Percepção → Planejamento → Decisão → Ação → Observação, o padrão ReAct, critérios de parada, retries e controle de autonomia: como o agente decide, a cada passo, se consulta mais, se já tem o suficiente, ou se desiste.
