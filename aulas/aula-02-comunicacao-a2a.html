Aula 2 · Protocolos de Comunicação Agente-a-Agente (A2A)

Agentes que conversam sem se conhecer

Na Aula 1 o extrator entregava o resultado direto para o humano. Conforme o SIGMA ganha um classificador, um auditor e um painel, amarrar tudo com chamadas diretas vira um nó. Esta aula troca as chamadas por mensagens: Request/Response, Pub/Sub, e os contratos de MQTT, gRPC e FIPA-ACL.

5h · laboratório Python · pub/sub · MQTT · gRPC pré: Aula 1 dados sintéticos

Bloco 1 · Abertura e contextualização

O problema: o SIGMA cresceu

O extrator da Aula 1 funciona. Agora a triagem quer mais: classificar a prioridade, manter uma trilha de auditoria de tudo que foi processado e alimentar um painel com os números do dia. Se cada peça chamar a próxima diretamente (classificador.classificar(extrator.extrair(texto))), em pouco tempo:

  • todo mundo precisa importar e instanciar todo mundo;
  • acrescentar o auditor obriga a mexer no extrator e no classificador;
  • se o classificador cair, o extrator cai junto;
  • não dá para rodar as peças em máquinas diferentes.

A saída é os agentes trocarem mensagens por um canal comum, em vez de se chamarem. Hoje construímos esse canal — primeiro em memória, depois sobre MQTT e gRPC.

Objetivos

Ao final, o estudante será capaz de:

  • Distinguir comunicação síncrona de assíncrona, escolhendo o padrão certo para uma tarefa do SIGMA

  • Modelar um contrato de mensagem inspirado na FIPA-ACL, com performativa e ontologia
  • Mapear o mesmo fluxo para MQTT e para gRPC, apontando o que muda em cada transporte
  • Justificar, por enlace, a escolha de transporte considerando latência, acoplamento e risco de falha
  • Reconhecer os riscos que a mensageria adiciona (spoofing, vazamento) e suas mitigações

Bloco 2 · Fundamentos teóricos

Síncrono × assíncrono

Na comunicação síncrona quem envia para e espera a resposta — como um telefonema. Na assíncrona, envia e segue a vida; a resposta (se houver) chega depois — como um e-mail. Não é "melhor" e "pior": é acoplamento no tempo. Síncrono é simples de raciocinar e ruim de escalar; assíncrono escala e é mais difícil de depurar.

Request/Response — o telefonema

O chamador conhece o serviço, manda um pedido e bloqueia até a resposta. É o modelo de REST e de gRPC. Bom quando você precisa da resposta para continuar ("classifique esta ocorrência agora, vou mostrar na tela").

sequenceDiagram participant T as Triagem participant C as Classificador T->>C: REQUEST classificar(ocorrência) Note right of C: aplica a regra C-->>T: CONFIRM prioridade = alta, revisar = true

Simples e direto — mas se o Classificador estiver fora do ar, a Triagem trava ou recebe erro.

Pub/Sub — o mural

Quem produz publica um evento num tópico e não sabe (nem se importa) quem lê. Quem tem interesse assina o tópico. Um broker no meio faz a entrega. Acrescentar um novo consumidor não toca em ninguém.

flowchart LR E["Extrator"] -- "publica: ocorrencia.extraida" --> B[["barramento / broker"]] B --> C["Classificador"] B --> A["Auditor"] B --> P["Painel"] C -- "publica: ocorrencia.classificada" --> B

O Extrator não conhece o Classificador. O Painel foi acrescentado sem mexer em nada.

Eventos, filas e mensageria

TermoO que é
Evento"Isto aconteceu" — fato no passado, imutável (ocorrencia.extraida).
MensagemQualquer envelope trafegado: evento, comando ou resposta.
FilaUm consumidor por mensagem, com ordem e retentativa (trabalho a fazer).
Tópico (pub/sub)Todos os assinantes recebem cada mensagem (notificação).
BrokerO intermediário que roteia, entrega e (às vezes) guarda mensagens.
BackpressureO que fazer quando chega mais rápido do que se consome.

MQTT — pub/sub leve, feito para muitos clientes

Protocolo de mensageria sobre TCP, criado para telemetria e IoT: cabeçalho minúsculo, milhares de conexões, tópicos hierárquicos separados por /. Um broker (ex.: Eclipse Mosquitto) recebe os PUBLISH e distribui aos assinantes.

flowchart TD R["sigma/# (tudo)"] --> O["sigma/ocorrencia/+ (um nível)"] O --> E["sigma/ocorrencia/extraida"] O --> K["sigma/ocorrencia/classificada"] R --> S["sigma/sistema/heartbeat"]

A árvore é só o espaço de nomes dos tópicos. Quem assina escolhe o nível: sigma/ocorrencia/extraida pega um tópico exato; sigma/ocorrencia/+ pega extraídas e classificadas; sigma/# (o Auditor) pega tudo, inclusive o heartbeat do sistema.

  • Curingas na assinatura: + = um nível; # = tudo dali para baixo. O Auditor assina sigma/#.
  • Segurança: autenticação usuário/senha, TLS, e ACL por tópico — quem pode publicar/assinar o quê.

Leitura de referência (ver Glossário, não é preciso deter-se ao vivo): QoS 0/1/2 — "no máximo uma vez" / "pelo menos uma vez" / "exatamente uma vez", mais garantia = mais latência; Retain — o broker guarda a última mensagem do tópico para quem chegar depois.

gRPC — Request/Response tipado e rápido

Framework RPC sobre HTTP/2. O contrato é um arquivo .proto obrigatório: define serviços, métodos e mensagens. Um compilador gera o código de cliente (stub) e servidor. O payload trafega em binário (Protocol Buffers), não JSON — menor e mais rápido de serializar. (Streaming — ver Glossário — é leitura de referência nesta aula.)

grpc_demo/classificador.proto
syntax = "proto3";
package sigma.a2a.v1;

service Classificador {
  rpc Classificar(OcorrenciaExtraida) returns (Classificacao);
}

message OcorrenciaExtraida {
  string id = 1;
  string natureza = 2;
  string data_fato = 3;
  string local = 4;
  string resumo = 5;
}

message Classificacao {
  string id = 1;
  string natureza = 2;
  string prioridade = 3;
  bool   revisao_humana_obrigatoria = 4;
}

Além do unary (um pedido, uma resposta), o gRPC tem streaming nos dois sentidos — útil quando um agente precisa acompanhar um fluxo contínuo (Aula 4).

FIPA-ACL — a semântica da mensagem

A FIPA Agent Communication Language é um padrão (anos 2000) que não define transporte, e sim a estrutura e a intenção da mensagem. O campo central é a performativa (ou "ato comunicativo"):

PerformativaSignificaNo SIGMA
informcomunico um fatoExtrator anuncia ocorrencia.extraida
requestpeço uma açãoTriagem pede "classifique já"
query-refpergunto o valor de algo"qual a prioridade da SIM-0002?"
agree / refuseaceito / recuso executarClassificador recusa ontologia desconhecida
failuretentei e não conseguierro no handler vira resposta failure

Outros campos: sender, receiver, conversation-id (amarra a troca), ontology (o vocabulário do conteúdo), reply-with. Nosso EnvelopeA2A é um subconjunto pragmático disso, em JSON.

Peça 1 — o envelope (contrato)

Toda mensagem do SIGMA é um EnvelopeA2A. A performativa diz a intenção; conteudo é validado por quem recebe.

app/mensagem.py
import uuid
from datetime import datetime, timezone
from enum import Enum
from pydantic import BaseModel, Field

class Performativa(str, Enum):
    INFORM = "inform"
    REQUEST = "request"
    CONFIRM = "confirm"
    REFUSE = "refuse"
    FAILURE = "failure"
    NOT_UNDERSTOOD = "not-understood"     # (arquivo tem mais)

class EnvelopeA2A(BaseModel):
    performativa: Performativa
    remetente: str
    destinatario: str | None = None       # None = mensagem de tópico
    topico: str
    conversa_id: str = Field(default_factory=lambda: str(uuid.uuid4()))
    responder_a: str | None = None
    ontologia: str = "sigma/ocorrencia/v1"
    conteudo: dict = Field(default_factory=dict)
    enviado_em: str = Field(default_factory=lambda: datetime.now(timezone.utc).isoformat())

    @classmethod
    def informar(cls, remetente, topico, conteudo, **kw):
        return cls(performativa=Performativa.INFORM, remetente=remetente,
                   topico=topico, conteudo=conteudo, **kw)

    def resposta(self, remetente, performativa, conteudo):
        return EnvelopeA2A(performativa=performativa, remetente=remetente,
            destinatario=self.remetente, topico=self.responder_a or f"{self.topico}.resposta",
            conversa_id=self.conversa_id, ontologia=self.ontologia, conteudo=conteudo)

Peça 2 — o transporte (interface + pub/sub em memória)

Mesma ideia da Aula 1: o agente conhece só a interface. Trocar o barramento local pelo MQTT não muda uma linha dos agentes.

app/transporte.py
import fnmatch
from typing import Callable, Protocol
from .mensagem import EnvelopeA2A

Assinante = Callable[[EnvelopeA2A], None]

class Transporte(Protocol):
    def publicar(self, envelope: EnvelopeA2A) -> None: ...
    def assinar(self, filtro_topico: str, callback: Assinante) -> None: ...

class BarramentoLocal:
    """Entrega síncrona e ordenada. Curingas fnmatch: 'ocorrencia.*', '*'."""
    def __init__(self):
        self._assinantes: list[tuple[str, Assinante]] = []
        self.entregues = 0

    def assinar(self, filtro_topico, callback):
        self._assinantes.append(("*" if filtro_topico == "#" else filtro_topico, callback))

    def publicar(self, envelope):
        for filtro, callback in list(self._assinantes):
            if fnmatch.fnmatch(envelope.topico, filtro):
                self.entregues += 1
                callback(envelope)

Para o Request/Response há um ServicoLocal: um registro de handlers em que chamar(nome, envelope) devolve a resposta — e levanta ServicoNaoEncontrado se o serviço não estiver registrado (é o acoplamento aparecendo).

Peça 3 — os três agentes

app/agentes.py
class AgenteExtrator:
    nome = "extrator"
    def publicar_todas(self, barramento):
        for item in self._ocorrencias:
            conteudo = {"id": item["id"], **extrair(item["texto"])}
            barramento.publicar(EnvelopeA2A.informar(self.nome, "ocorrencia.extraida", conteudo))

class AgenteClassificador:
    nome = "classificador"
    def ao_receber(self, env):                       # assíncrono (pub/sub)
        resultado = classificar(env.conteudo)
        self._barramento.publicar(EnvelopeA2A(
            performativa=Performativa.INFORM, remetente=self.nome,
            topico="ocorrencia.classificada", conversa_id=env.conversa_id,
            conteudo={"id": env.conteudo.get("id"), **resultado}))
    def responder(self, env):                         # síncrono (request/response)
        return env.resposta(self.nome, Performativa.CONFIRM, classificar(env.conteudo))

class AgenteAuditor:
    nome = "auditor"
    def ao_receber(self, env):
        self.trilha.append(env)                       # trilha imutável — só acrescenta

Nível intermediário

Request/Response, performativas e acoplamento

Quando a Triagem precisa da classificação na hora (para exibir na tela), pub/sub não serve — ela quer uma resposta. Aí entra o ServicoLocal.

exemplo — request/response com recusa por ontologia
servico = ServicoLocal()

def handler(env):
    if env.ontologia != "sigma/ocorrencia/v1":
        return env.resposta("classificador", Performativa.REFUSE,
                            {"motivo": f"ontologia não suportada: {env.ontologia}"})
    return classificador.responder(env)               # devolve CONFIRM

servico.registrar("classificador", handler)

ok   = EnvelopeA2A.pedir("triagem", "classificar", {...}, responder_a="r")
ruim = ok.model_copy(update={"ontologia": "outro/v9"})

servico.chamar("classificador", ok).performativa      # -> confirm
servico.chamar("classificador", ruim).performativa    # -> refuse

Bloco 6 · Desafio

Nível avançado

Distribuir o SIGMA

Cada agente vira um processo separado, possivelmente em outra máquina. Você escolhe o transporte de cada enlace pela necessidade: evento que muitos ouvem → MQTT; "responda agora" → gRPC.

flowchart LR subgraph p1["Processo: Extrator"] EX["AgenteExtrator"] end subgraph bk["Broker MQTT"] BK[["sigma/#"]] end subgraph p2["Processo: Classificador"] CL["AgenteClassificador"] GS["gRPC :50051"] end subgraph p3["Processo: Auditor"] AU["AgenteAuditor + armazenamento"] end EX -- "MQTT publish: ocorrencia.extraida" --> BK BK -- "assina: ocorrencia.extraida" --> CL CL -- "MQTT publish: ocorrencia.classificada" --> BK BK -- "assina: sigma/#" --> AU UI["Triagem (tela)"] -- "gRPC Classificar()" --> GS

Cada caixa é um processo isolado. As setas do Extrator, Classificador e Auditor passam todas pelo broker MQTT (assíncrono, ninguém conhece ninguém). A única seta que não passa pelo broker é a da tela de Triagem: ela chama o Classificador direto por gRPC porque precisa da resposta na hora. O mesmo AgenteClassificador atende os dois caminhos.

Bloco 7 · Debriefing

Trade-offs e riscos

Quando cada padrão

SituaçãoEscolha
Preciso da resposta para continuarRequest/Response (gRPC, REST)
Vários interessados no mesmo fato; a lista mudaPub/Sub (MQTT)
Trabalho a processar, uma vez, com retentativaFila
Contrato rígido entre times internosgRPC (.proto)
Integração com sistema externo/legadoREST/HTTP

Custo do assíncrono: mais partes móveis (broker é infraestrutura para manter, monitorar, escalar), depuração mais difícil (o fluxo não está numa pilha de chamadas), e você precisa lidar com entrega duplicada, fora de ordem e mensagens "envenenadas".

Segurança do barramento

⛔ Spoofing de tópico

Sem autenticação, qualquer processo publica ocorrencia.classificada com "prioridade baixa" e enterra um caso. Mitigação: broker com auth + ACL por tópico, TLS/mTLS, e assinatura/verificação do envelope.

⛔ Envelope não confiável

O conteudo que chega pode ser malformado ou hostil (a mesma lógica de prompt injection da Aula 1). Valide contra o schema antes de agir; rejeite ontologia desconhecida com refuse.

⛔ Broadcast vaza dados

Quem pode assinar sigma/#? O Auditor sim; um serviço de terceiros, não — seria acesso a todo o fluxo de ocorrências (risco LGPD). Least privilege por tópico na ACL.

  • Trilha imutável = base de auditoria. O Auditor só acrescenta. Isso vira observabilidade e prova de rastreabilidade na Aula 9.
  • Protótipo ≠ produção. O BarramentoLocal é síncrono e sem falhas; um broker real tem QoS, dead-letter, particionamento.
⚠️ Ponto de atenção — uso responsável

O barramento apenas distribui mensagens — ele não cria autoridade. A "prioridade" e o "revisar" continuam sendo rascunho de triagem. Nenhuma mensagem no SIGMA determina autoria, indiciamento ou medida cautelar; a decisão permanece com o servidor, e a trilha do Auditor existe justamente para tornar cada passo automatizado auditável.

Problema de transferência

Mensageria para um mandado de busca sintético

Um mandado de busca sintético passa por: emissão → cumprimento (diligência) → apreensão de itens → encerramento. Projete a comunicação entre os agentes envolvidos (não precisa terminar de codificar):

  1. Liste os eventos (ex.: mandado.emitido, diligencia.iniciada, item.arrecadado, mandado.cumprido) e classifique cada enlace como Pub/Sub ou Request/Response — justifique.
  2. Onde entra ACL por tópico? Quem deveria poder publicar item.arrecadado?
  3. O que trafega em cada mensagem (o conteudo mínimo) para servir de prova depois?

Não há gabarito único — o objetivo é decidir e justificar.

Exercício prático

Acrescente um tópico ocorrencia.arquivada e um AgenteArquivador que assina ocorrencia.classificada, e — só para prioridade normal sem revisão — publica ocorrencia.arquivada. O Auditor deve registrar os três tipos de evento. Testes continuam verdes.

Desafio

Escreva um teste que prove que uma mensagem publicada em ocorrencia.classificada por um remetente que não seja "classificador" é ignorada por um novo guardião (primeira linha de defesa contra spoofing, em código).

Glossário

Síncrono
Quem envia bloqueia até a resposta chegar.
Assíncrono
Quem envia segue adiante; a resposta, se houver, chega depois.
Request/Response
Padrão em que o chamador conhece o serviço e espera o retorno.
Pub/Sub
Produtor publica em um tópico; assinantes interessados recebem. Produtor e consumidor não se conhecem.
Broker
Intermediário que roteia e entrega mensagens (ex.: Mosquitto para MQTT).
MQTT
Protocolo de mensageria pub/sub leve, sobre TCP, criado para telemetria/IoT; tópicos hierárquicos e broker central.
Tópico
Canal nomeado, hierárquico (sigma/ocorrencia/extraida).
Curinga (MQTT)
Na assinatura: + casa um nível; # casa tudo dali para baixo (sigma/ocorrencia/+, sigma/#).
Fila
Cada mensagem é consumida por um único trabalhador, com ordem e retentativa.
Envelope
A mensagem completa que trafega: metadados (remetente, tópico, performativa, conversa) + o conteudo.
QoS (MQTT)
Garantia de entrega: 0 (no máximo uma vez), 1 (pelo menos uma), 2 (exatamente uma).
Retain (MQTT)
O broker guarda a última mensagem do tópico para novos assinantes.
ACL por tópico
Regra no broker que define quem pode publicar e quem pode assinar cada tópico — a defesa principal contra publicação forjada.
TLS / mTLS
Criptografia do transporte; no mTLS os dois lados apresentam certificado, autenticando cliente e servidor.
RPC
Remote Procedure Call: chamar um método que executa em outro processo/máquina como se fosse local.
gRPC
Framework RPC sobre HTTP/2 com contrato .proto e payload binário.
Streaming (gRPC)
Modo em que cliente e/ou servidor enviam uma sequência de mensagens na mesma chamada, em vez de uma só.
Protocol Buffers
Formato de serialização binária, tipado, usado pelo gRPC.
Stub
Código de cliente gerado a partir do .proto; chama o método remoto como se fosse local.
FIPA-ACL
Padrão de linguagem de comunicação entre agentes: estrutura e intenção da mensagem.
Performativa
O ato comunicativo da mensagem: inform, request, refuse…
Ontologia
O vocabulário/esquema que dá sentido ao conteúdo da mensagem.
conversation-id
Identificador que amarra as mensagens de uma mesma troca.
Desacoplamento
Reduzir o quanto uma parte precisa saber sobre as outras.
Backpressure
Mecanismo para lidar com produção mais rápida que o consumo.

Classificador 30s fora do ar: no enlace MQTT, as ocorrencia.extraida ficam no broker (QoS 1 + sessão persistente) e são processadas quando ele volta — degradação graciosa. No enlace gRPC, a Triagem recebe UNAVAILABLE na hora — precisa de timeout, retry com backoff e um fallback (ex.: "classificação pendente").

Três falhas de segurança no desenho + mitigação: (1) broker sem auth/ACL → autenticação por serviço + ACL por tópico; (2) tráfego em claro → TLS no MQTT e mTLS no gRPC; (3) sem verificação de origem do envelope → assinar o envelope e o Auditor/consumidores rejeitarem remetente inesperado por tópico.

Avaliação — respostas-guia

  1. Síncrono bloqueia (gRPC da Triagem); assíncrono não (Extrator publicando eventos).
  2. Porque o Extrator publica num tópico e não chama ninguém; o Auditor só assina.
  3. Intenção: distinguir "informo um fato" de "peço uma ação" de "recuso" — muda como o receptor deve reagir.
  4. MQTT: pub/sub, assíncrono, payload livre, broker. gRPC: req/resp, síncrono, contrato .proto, binário.
  5. Publicar evento forjado (classificação falsa); mitigação: ACL por tópico + autenticação + assinatura do envelope.

Exercício prático (Arquivador): novo assinante de ocorrencia.classificada que republica ocorrencia.arquivada só quando prioridade == "normal" e not revisao_humana_obrigatoria. Cuidado com laço: o Arquivador não pode assinar o próprio tópico.

Desafio (guardião anti-spoofing): um wrapper de assinatura que só repassa ao callback se env.remetente == esperado_por_topico[env.topico]. É a versão em código do que a ACL do broker faria em produção.

Evolução do SIGMA — Aula 2

Os agentes agora conversam por um barramento, sem se conhecerem, e cada mensagem carrega sua intenção. Na Aula 3 damos ao agente algo que ele ainda não tem: acesso controlado a ferramentas e dados externos — uma base de consultas, uma API — através do Model Context Protocol (MCP). O barramento distribui; o MCP dá poder de agir, com autorização.

flowchart LR O[("Boletim sintético")] --> E["Extrator"] E -- "inform" --> BUS[["barramento A2A"]] BUS --> C["Classificador"] BUS --> A["Auditor — trilha"] C -- "inform" --> BUS C --> H["Revisão humana"] UI["Triagem"] -- "request (gRPC)" --> C

Comparado com o fim da Aula 1, o que mudou: entre o Extrator e a decisão humana entrou um barramento. O Extrator só publica inform; Classificador e Auditor reagem sem serem chamados; e a tela de Triagem tem um atalho síncrono (gRPC) para pedir uma classificação sob demanda.

"Trocar chamadas por mensagens não é sofisticação gratuita: é o que permite acrescentar um auditor sem pedir licença a ninguém — e é também uma nova porta que alguém pode tentar arrombar."
